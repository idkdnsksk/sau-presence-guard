# Безопасность, персональные данные и модель угроз

## Защищаемые свойства

- QR выпущен backend, не изменён и ещё действует.
- QR относится к текущему занятию и назначенному ведущему.
- запрос сделан авторизованным участником группы.
- координаты получены непосредственно при отметке и согласуются с местом и ведущим с учётом accuracy.
- запрос пришёл из подлинного приложения на допустимом физическом устройстве.
- повтор не создаёт вторую отметку, а ручное решение не стирает историю.

## Угрозы и меры

| Угроза | Мера |
|---|---|
| Изменить занятие/срок в QR | HMAC-SHA-256 по header+payload, constant-time verify, key ID. |
| Переслать скриншот позднее | 15-секундный server TTL, журнал факта выдачи, динамическое обновление. |
| Изменить время телефона | Расписание и TTL вычисляются по server UTC. |
| Повторить запрос | One-use attestation challenge, App Attest sign count, уникальность attendance. |
| Подменить GPS | OS mock flag, Play Integrity/App Attest, emulator/root signals, двойная геодистанция и история. |
| Отметиться из другой точки | Место + свежая позиция ведущего; hard/soft thresholds с accuracy. |
| Передавать телефон между аккаунтами | Случайный installation secret хранится secure storage, на сервер уходит только SHA-256; разные группы с одним hash → suspicious. |
| Быстро сменить город | Расчёт расстояния и скорости между недавними попытками → suspicious. |
| Подменить Flutter-клиент | Сервер не доверяет клиентскому статусу; production attestation привязана к package/bundle и canonical payload. |
| Проверяющий перезапишет решение | Review только из `suspicious`, сохраняются original status, append-only history и audit. |
| Массовый перебор API | Auth, role checks, schema limits, body limit, CORS и rate limits. |

## Классификация сигналов

Hard reject: неверный/истёкший QR, невалидная attestation, mock location, emulator, устаревшая координата, занятие вне окна, явно далёкая точка.

Manual review: слабая accuracy, root/jailbreak при прошедшей платформенной attestation, мягкое превышение радиуса, устаревшая позиция ведущего, shared device разных групп, невозможный скачок.

Root/jailbreak heuristics сами по себе обходятся и поэтому не используются как единственный источник истины. Основной сигнал доверия — platform attestation, а эвристика повышает риск.

## Персональные данные в Республике Казахстан

Геолокация и история посещений требуют формального решения владельца системы о законном основании, согласии, сроке хранения, доступах и уничтожении. Официальные источники для проверки политики перед production:

- [Закон РК «О персональных данных и их защите»](https://adilet.zan.kz/rus/docs/Z1300000094);
- [Правила осуществления мер по защите персональных данных](https://adilet.zan.kz/rus/docs/V2600039823);
- [Комитет информационной безопасности — обязанности собственников и операторов](https://www.gov.kz/memleket/entities/infsecurity/activities/30?lang=ru).

Этот документ — инженерная мера, не юридическое заключение. Перед запуском ответственный юрист/ИБ заказчика утверждает DPIA/реестр обработки и пользовательские тексты.

Рекомендуемый baseline:

- явное согласие/уведомление до первой отметки;
- цель: только подтверждение посещаемости и разбор fraud;
- foreground GPS только при действии пользователя, без фонового трекинга;
- не передавать координаты картографическому сервису;
- хранить production-БД и резервные копии в утверждённой инфраструктуре на территории РК;
- exact coordinates в `attendance_attempts` хранить ограниченный период (например, 30 дней после закрытия спора), затем удалить или огрубить; конкретный срок утверждает заказчик;
- attendance fact можно хранить по основной политике продукта, отдельно от raw signals;
- роли least privilege: участник видит своё, ведущий — свои занятия, администратор — очередь/настройки; доступ к raw GPS отдельно;
- журналировать чтение/экспорт raw location в production;
- поддержать отзыв согласия, запрос субъекта и регламент удаления;
- шифрование in transit, encrypted storage/backups, secret manager и ротация ключей.

## Данные, которые не нужны

- IMEI, serial, advertising ID и аппаратные идентификаторы;
- непрерывный маршрут пользователя;
- список контактов, Wi-Fi SSID или Bluetooth devices;
- фото/видеозапись сканирования;
- точные координаты у стороннего map provider.

## Эксплуатационные алерты

- рост `QR_SIGNATURE_INVALID` может означать tampering или рассинхрон ключей;
- рост `PLAY_INTEGRITY_UNAVAILABLE` — внешняя деградация, её нельзя смешивать с fraud;
- резкий рост `LOW_GPS_ACCURACY` по одному месту требует настройки радиуса/порогов;
- очередь `suspicious` без решения дольше SLA;
- повторные `SIGN_COUNT_REPLAY` и `INTEGRITY_CHALLENGE_USED`;
- изменение правил места и QR secret вне change window.

## Известные ограничения

- Геолокация вероятностна, особенно в помещении; поэтому accuracy влияет на решение.
- Root/jailbreak detection не может быть абсолютно полным.
- Короткий QR не предотвращает live relay человеку с настоящим устройством внутри разрешённой зоны.
- Реальные Play Integrity/App Attest нельзя честно проверить без release signing и credentials заказчика. Demo path существует только для приёмочного стенда и запрещён кодом в production.
